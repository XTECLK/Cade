Set up
Connect with your existing agent

Bring your own agent. Every tool says what it takes and gives back.

How to connect your own AI agent to Cade, and every tool it gets, generated from the server's own tool definitions, so it is always what an agent sees in tools/list. A result is text and, matching its schema, structuredContent, so an agent can pass one tool's IDs to the next.

Connect your agent

1. In Slack open Cade's Home tab, press Settings, then AI agent and Create key. Cade shows the key to you only, once, with this Cade's MCP endpoint (the same window shows the endpoint again, and whether you have a key). Revoke key in the same window ends it.

2. Add Cade to your agent as a remote MCP server (Streamable HTTP), with the key in the header x-apikey. Replace the two placeholders with the endpoint and key from step 1:

Claude Code

claude mcp add --transport http cade https://YOUR-CADE-WORKER/mcp --header "x-apikey: YOUR_API_KEY"

Gemini CLI

gemini mcp add --transport http cade https://YOUR-CADE-WORKER/mcp --header "x-apikey: YOUR_API_KEY"

Cursor, Codex and other clients

Add a remote MCP server with the endpoint and the header x-apikey set to your key. The Claude.ai and Gemini web apps can't send a custom header, so they can't connect yet.

3. Ask your agent something like "list my Cade tasks". Everything runs as you, so it reads only what you can read, and anything that changes a task or posts a message is shown to you first.

Prompts

Workflows built on the tools, which Cade offers as MCP prompts: you pick one in your agent, and it follows its steps, showing you everything before it's written. In Claude Code each is a slash command, such as /mcp__cade__task-summary followed by its arguments; other clients list them in their own way. A team's prompts are its own, kept in its deploy repo (prompts/): the cade-deploy template starts with a task's summary and an executive summary, to change or add to. See Workflows.

get_task

Reads one task from Cade's own database: its details, people, links, summary and notes. It includes no thread, but names the one the task was made from, which get_thread_history reads. It names the task's subtasks too (parts of it, or issues found while testing it), each with its own thread, which get_task_history reads: read them as well to know how the whole task went, such as for an executive summary.

create_task

Creates a task, or an incident, in a project's channel as the person you act for: from a Slack thread (moved into the new task) or from scratch, with its summary saved on the notes page. An incident is always Urgent and due immediately. Suggest the title, priority, due date and summary and ask for the person's input, and call this only with a task the person has seen and approved. Check with get_tasks that the task doesn't exist already. Each call makes a new task. Offer to assign people afterwards with update_task. With parent_task_id it makes a subtask of that task instead (a part of it, or an issue found while testing it): in the task's project, with its own card and thread, starting with the task's people and due date (give another if it is due earlier or later), and with its priority for good, which follows the task's; the task's thread is told, with a link. Subtasks go one level deep, and a subtask of an incident is an incident too. A task moves to Client review or Done only once all its subtasks are Done. Preview: kind (task or incident), title, project, priority, due date (or none), the whole summary, the thread it comes from, and the task it is a subtask of, if any.

Arguments inputSchema

NameTypeRequiredNotes
titlestringyesOne short line saying what has to be done
projectstringThe project to make it in, by the name get_projects gives. Can be left out when the thread is in a project's channel or there is only one project
prioritystring: Urgent | High | Medium | LowDefault Medium. Not for an incident
due_datestringDD/MM/YYYY or YYYY-MM-DD. Use a date the thread gives or clearly implies, never an invented one; leave out for none. Not for an incident
incidentbooleanMake an incident: only for something broken now that blocks people or the business, always Urgent and due immediately. When unsure, leave it false (a task). Default false
summarystringThe summary of the issue only, saved on the notes page: what the problem or request is, who raised it and when, the impact and the details needed to understand it, for someone who wasn't in the discussion. Write it from the thread it is made from, and leave out what that thread doesn't say. Plain text, people's names rather than @mentions. At most 8000 characters
thread_idstringThe thread to make it from. One that is already a task, was moved into one, or is a bot's or a direct message can't be used

update_task

Changes a task in one call: its status, priority, due date, people, pull requests and the summary on its notes page. Cade posts the field changes in the task's thread; a changed summary is saved and the thread is told, with a link to the notes page. Cade doesn't ask anyone to do anything: when the change means asking people (picking it up, reviewing, testing), suggested_message has the request. Ask the person whether to send it, as it is, in their own words or not at all (they may know it isn't needed), and send their version with send_thread_message only after a clear yes. A task with open subtasks can't move to Client review or Done: the call is refused, naming them. Ask the person whether to close them; if they agree, set each to DONE (with the usual preview), then move the task. Keeping it in step with the thread and the work: a status the evidence has moved past (To do when work has started, In progress when a pull request is up for review, or a message saying "ready for review", "QA passed" or "done"); a pull request mentioned or opened for it and not linked, to add; one linked and still open but replaced by another, or for another task, to remove. Offer nothing from a plan, a question or a guess. Preview: the task, then each field you change as old -> new with the reason (status, priority, due date, owner, reviewer, tester, pull requests, summary), and nothing left unchanged. Call this only with changes the person has seen and approved.

statusstring: TODO | IN_PROGRESS | IN_REVIEW | IN_TESTING | CLIENT_REVIEW | DONEThe task's new status. A task in Client review can't be changed here: its approver decides. CLIENT_REVIEW and DONE need all the task's subtasks Done first

send_approval_request

Asks a person to approve a task that is in Client review: posts a request in the task's thread that mentions them, with Approve and Not approve buttons only they can click. Approving moves the task to Done; not approving sends it back to In progress. The request says "Could you take a look and approve it, or let us know what needs to change?" to them, unless the person words it their own way in message. Preview: the task, who will be asked to approve it, and the request as it will be posted. Call this only with an approver and request the person has chosen and approved. Each call posts a new request.
