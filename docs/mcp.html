Set up
Connect with your existing agent

Bring your own agent. Every tool says what it takes and gives back.

How to connect your own AI agent to Cade, and every tool it gets, generated from the server's own tool definitions, so it is always what an agent sees in tools/list. A result is text and, matching its schema, structuredContent, so an agent can pass one tool's IDs to the next.

Connect your agent

1. In Slack send /cade mcp init. Cade shows the key to you only, once, with this Cade's MCP endpoint (/cade mcp status shows the endpoint again, and whether you have a key). /cade mcp revoke ends the key.

2. Add Cade to your agent as a remote MCP server (Streamable HTTP), with the key in the header x-apikey. Replace the two placeholders with the endpoint and key from step 1:

Claude Code

claude mcp add --transport http cade https://YOUR-CADE-WORKER/mcp --header "x-apikey: YOUR_API_KEY"

Gemini CLI

gemini mcp add --transport http cade https://YOUR-CADE-WORKER/mcp --header "x-apikey: YOUR_API_KEY"

Cursor, Codex and other clients

Add a remote MCP server with the endpoint and the header x-apikey set to your key. The Claude.ai and Gemini web apps can't send a custom header, so they can't connect yet.

3. Ask your agent something like "list my Cade tasks". Everything runs as you, so it reads only what you can read, and anything that changes a task or posts a message is shown to you first.

Flows

Step-by-step jobs your agent follows with get_flow, which Claude Code also lists as slash commands:

  • summarize_task: Write a task's summary: the issue, from the thread the task was made from. What was done and how it ended stay in the task's own thread.
  • triage_tasks: Go through tasks one at a time: read the threads, propose the status, priority, due date and people, and apply them after you approve.
  • explain_task: Tell me about a task as Issue, Action and Result, from the thread it was made from and its own thread. Saves nothing.
  • check_prs: Check the status of a task's pull requests in the repository, and unlink those closed without merging, after you approve.
  • report_progress: Write a progress update from this repository's commits and pull request, post it in the task's thread and link the pull request, after you approve.
  • plan_my_work: Look at my open tasks and suggest what to do first. Saves nothing.
  • create_task_from_thread: Read a Slack thread, suggest a title, kind, priority, due date and summary, take your input, and create the task or incident after you approve it.
  • create_task_from_scratch: Make a new task or incident from what you tell me, with a suggested title, priority and due date, after you approve it.
  • browse_channels: List the channels Cade is in, browse a channel's recent conversations it doesn't track yet, look into one and make a task or incident from it after you approve.

create_task

Creates a task, or an incident, in a project's channel, as the person you act for: either from a Slack thread (the thread's first message is moved into the new task's thread, as Cade's New task shortcut does) or from scratch. Call this only with a task the person has seen and approved: suggest the title, priority, due date and summary, ask for their input, show the final version and ask again, and never create one unasked. Each call makes a new task, so don't call it twice for the same thing. title is one line, at most 150 characters. priority is one of Urgent, High, Medium, Low (Medium by default); due_date is DD/MM/YYYY or YYYY-MM-DD, or leave it out for none. An incident (incident: true) is always Urgent and due immediately, so give it neither priority nor due_date. project is a name from get_projects; it can be left out when the thread is in a project's channel or there is only one project. To make it from a thread give thread_id or link, as for get_thread_history (read the thread first, from get_channel_threads or the person's link); a thread that is already a task, was already moved into one, or is a bot's or a direct message can't be used. summary is saved on the task's notes page as update_task would: the issue only, as plain text, at most 8000 characters. update_task

Changes a task in one call: its status, priority, due date, who is its owner, reviewer or tester, and the summary on its notes page. Every argument but the task is optional: give only what changes, at least one. Cade posts the changes to the fields in the task's thread, as the person you act for, and asks the people it assigns to pick it up; the summary is saved quietly on the notes page. Call this only with changes the person has seen and approved: show them what you propose to change and why, and ask first. Status is one of TODO, IN_PROGRESS, IN_REVIEW, IN_TESTING, CLIENT_REVIEW, DONE. Priority is one of Urgent, High, Medium, Low. due_date is DD/MM/YYYY or YYYY-MM-DD, or "none" to remove it. owner, reviewer and tester each take { add: [user IDs], remove: [user IDs] }; find a person's ID with find_user_by_name. prs takes { add: [pull request links], remove: [links] } to link or unlink pull requests (GitHub, GitLab or Bitbucket); adding asks the task's reviewers to review it, and one already sent to the client for approval can't be removed here. An incident's priority and due date never change. The summary is of the issue only, taken from the thread the task was made from (named by get_task, read with get_thread_history): what the problem or request is, who raised it and when, the impact and the details needed to understand it. Leave out what was done and how it ended, which the task's own thread (get_task_history) already has. For someone who wasn't in the discussion. Plain text only, as the page shows markup as it is: short paragraphs, "- " for bullets, and people's names rather than @mentions. At most 8000 characters, and it replaces any earlier summary. Takes the task's ID, as get_tasks gives it.

Arguments inputSchema

NameTypeRequiredNotes
