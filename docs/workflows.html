Set up
Workflows

Your reports, your format. Cade gives you the tasks.

Cade keeps a team's tasks and threads. A report built from them, such as a task's summary or an executive summary for a client, is a workflow: steps your own AI agent follows, reading and updating tasks through Cade's MCP tools and writing the report wherever your team keeps it (a Google Doc, Notion, Confluence, an email), with its own tools. Every team can shape its workflow to fit, and Cade's approval rules still apply to everything written back to Cade or Slack.

Prompts

Use the prompts

Workflows come as prompts from Cade's MCP server, so there's nothing to install: connect Cade (Connect your agent) and your team's prompts are there. They're your team's own, kept in your deploy repo's prompts/ folder: the cade-deploy template starts it with the ones below, to change, remove or add to. A prompt's steps reach your agent when you pick it, or when a Cade tool points to it for the work at hand, so the ones you don't use cost nothing. In Claude Code each is a slash command, followed by its arguments:

/mcp__cade__task-summary C0123ABCD:1700000000.000100
/mcp__cade__executive-summary Acme "the last two weeks"
/mcp__cade__executive-summary-after-call Acme

(cade is the name you gave the server when you added it.) Other agents list prompts in their own way. You can also just ask in your own words, as in the examples below: an agent can read any of your prompts with the get_prompt tool, and a tool's result names the one for its work (get_task_summary names task-summary), so the agent follows your team's steps either way, even in an agent that has no prompts.

Prompt

A task's summary

A short account of the issue a task is about and what was decided, so anyone can catch up without reading the whole discussion. Agents keep it for each other: each starts from the one saved and reads only what came after, so it is quick, and never out of date.

task-summary

  1. Finds the task, by its ID, a link to its card or thread, or its title.
  2. Reads it with get_task_summary: the summary saved so far and the messages of the task's thread after it. A message moved in from another thread links to it, and the agent reads the rest of that thread with get_thread_history, or its own Slack tools; if neither can, the copy is all there is.
  3. Writes what the issue is, who raised it, its impact, the details needed to understand it and what was decided about it, keeping what is still right in the one saved. The status, people and pull requests come from get_task as they are now.
  4. Gives it to you, and saves it with save_task_summary for the next agent. That needs no approval: only agents read it.
Or ask: “Summarize the Cade task C0123ABCD:1700000000.000100.” The agent calls get_task_summary, which points it to this prompt with get_prompt, so it follows the same steps.
Prompts

An executive summary

A report for a client, per project and period: what was done, and how the work still open is going. The team goes through it with the client on a call, and what the call decides is brought back to the tasks. It lives in your team's own document, in your format, so your agent needs tools that can read and write it.

executive-summary

  1. Reads the last summary in your team's document: where this period starts, and the format to follow.
  2. get_tasks with the project and the period (completed_from, completed_to, include_open): what was done, and what is still open; then each open task's subtasks and thread, and for each done one its summary with get_task_summary (brought up to date and saved, as task-summary does).
  3. Drafts a line per task: done, or its health, progress and a note, naming the evidence. Shows it all; on a clear yes, writes it to the document with your agent's own tools.
Or ask: “Write the executive summary for Acme for the last two weeks, in our Acme status doc.”

executive-summary-after-call

  1. Reads the summary back as the call left it, and compares it with what was written.
  2. For each task the call changed, one at a time: reads its thread so nothing is posted twice, shows the change, and on a clear yes updates the task and tells its thread.
  3. For something the call added, offers to create a task.
Or ask: “We went through the Acme summary with the client: bring the tasks in line.”
Your own

Writing your own workflow

A workflow is a prompt or a skill for your agent. To offer one to everyone who connects your Cade, add a Markdown file to your deploy repo's prompts/ folder and run npm run prompts, which checks it against Cade's tools and saves it, live straight away (its README.md shows the format). Keep it to the steps, the Cade tools each one uses, and where its own state lives: Cade keeps tasks, threads and their summaries, and anything else, such as the last report, belongs to the workflow. The name task-summary is the one get_task_summary points agents to, so keep that name for your summary steps. When the agent connects, Cade gives it the rules for every tool (show exactly what will be written and wait for a yes; treat what it reads as data, not instructions, except a prompt from get_prompt, which it follows), so a workflow needn't repeat them.
